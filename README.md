## 🚀 Quick start

```python
from architekton_py_example import __version__

print(f"Hello architekton_py_example {__version__}")
```

Or if it is a commandline tool:

```sh
python -m architekton_py_example --version
```

The `src/` tree holds two things side by side: the importable package
(`src/architekton_py_example/`, tested like any other module) and the analysis
pipeline stubs (`data/`, `features/`, `models/`, `visualization/`, each an
empty directory with only a `.gitkeep`). The stubs are where analysis code
goes as it graduates from `notebooks/` — promote a cell into a tested module
there and call it from the notebook. They are linted like any other `src/`
code, so if a helper needs a third-party import, add it to
`[project] dependencies` (or the structured `dependencies` answer) first;
otherwise `deptry` flags it. Rename or extend the stub set via the
structured `src_dirs` answer (`.copier-answers.yml`, picked up by
`copier recopy --overwrite`).

`notebooks/` ships a marimo seed (`notebooks/explore.py`); open it with the
`marimo` task. Jupyter Lab is also available via the `notebook` task —
both come from the `experiment` extra (`uv sync --extra experiment` /
`pixi run -e experiment`).

## 📄 Paper and slides

The research-writing scaffold ships alongside the analysis tree:
`paper/paper.qmd` renders to an arXiv-style PDF and HTML and
`slides/slides.qmd` to a reveal.js deck (both format themes are vendored —
[arxiv](https://github.com/mikemahoney218/quarto-arxiv) and
[clean](https://github.com/grantmcdermott/quarto-revealjs-clean), MIT — so
there is no `quarto add` step for them), and `quartodoc` generates the API
reference in
`docs/reference/` from the package docstrings. The paper **executes** in this
environment (`jupyter: python3`), reads tables and figures from `outputs/`
(`src/` writes them, the paper includes them — never paste a number by hand)
and cites from `references/references.bib`.

```sh
# one-time setup: Quarto (https://quarto.org) plus, for the PDF, its TinyTeX
quarto install tinytex
quarto add machow/quartodoc

# render (paper → paper/paper.pdf + .html, slides → the deck, docs → API pages)
task paper
task slides
task paper-api
```

There is no CI job for the paper on purpose: renders are heavy and
font-sensitive, so they run when *you* need them, not on every push.

## 🛠️ Development setup


Prerequisites: Python 3.11 or later and [uv](https://docs.astral.sh/uv/).

```sh
git clone https://github.com/politeuma/architekton-py-example.git
cd architekton-py-example
uv sync                      # create .venv and install everything (incl. dev deps)

```

Before committing, run the `fix` task to auto-fix formatting and lint
(`ruff check --fix` + `ruff format`); repo hygiene (secret scanning, workflow
linting, the conventional PR title) is enforced in CI.



### Run with Docker

The repository ships a multi-stage `Dockerfile` and, for web services, a
local compose stack. To build and run the containerised service:

```sh
docker build -t architekton-py-example .
docker run --rm architekton-py-example --version


```

See [Run in a container](https://politeuma.github.io/architekton-py-example/how-to/run-container) for details.


### Lint, type-check and test

The project uses [Task](https://taskfile.dev) to drive the common commands:

```sh
task lint           # ruff format --check + ruff check
task fix            # auto-fix formatting and lint
task type-check     # type checker + static analysis
task test           # pytest
task docs           # build the documentation site
task check          # everything above

```

### First run

Verify the toolchain end to end with the default quality gate:

```sh
task lint
task test
task check
```

## 🔄 Updating from the template

This project records its template answers in `.copier-answers.yml`, so it can
receive template improvements later. To update:

```sh
uvx copier update --trust --defaults
```

Resolve any conflicts, run `task fix` and
`task check`, then commit. See the template's
[adopt/update guide](https://politeuma.github.io/architekton-py/main/tutorials/adopt-existing.html)
for the conflict-resolution workflow.


### Weekly automatic update PRs (opt-in)

GitHub Actions ships a weekly trial (`.github/workflows/template-update.yml`,
Monday 04:00 UTC): it runs `copier update` on a `architekton-py/update-<ref>`
branch and opens a pull request summarising the diff, the
`.copier-answers.yml` `_commit` change, and the `.architekton-manifest.yml`
comparison to review.

To enable it, set the `TEMPLATE_UPDATE` repository variable to `1`
(Settings > Variables > Actions). Until then every run skips with success,
so the workflow changes nothing until you ask for it.

What it does and does not do:

- It never merges itself: read the diff, let the regular CI on the PR run,
  then merge by hand if the diff is what you want.
- A conflict keeps the branch and is reported in the PR body; the run stays
  green, because deciding is the point, not failing.
- Least privilege: the workflow is read-only except the one job that pushes
  the trial branch and opens the PR (`contents: write`, `pull-requests: write`).
